## 1. DBUS 遥控解码失败（最高优先级）

### 现象

```
g_dbus_ev  ≈ +72/秒        ← 接收机确实在发帧，串口也在收
g_dbus_ok  ≈ 0              ← 但几乎没有一帧通过 IsDbusFrameValid
rc_online  = 0              → 底盘卡在 Dead → 输出恒零
```

底盘和云台**都**受影响：云台的摇杆量来自底盘转发（`yaw_des`），
底盘 `rc=0` 时 `yaw_des` 恒为 0，所以云台也无法遥控。

### 已定位的事实

| 项 | 值 |
|---|---|
| 有信号的串口 | **USART3**（USART1/6 事件数恒 0） |
| UART 电气参数 | 100 kbaud / 8 数据位 / 偶校验，与 DBUS 一致 |
| UART 错误计数 | 0（说明不是波特率/校验错） |
| 原始缓冲（某次） | `00 00 04 00 04 20 00 D9 72 ...` |
| 同样数据偏移 2 字节后 | `data[5] = 0xD9` → left=3、right=1（**合法**） |

**结论：数据本身是好的，是接收窗口没有对齐。**

真实 DBUS 帧带 `0x20` 帧头，帧长不是 18；按 18 字节定长接收会让窗口
逐帧漂移，`data[5]`（拨杆字节）落到不同位置，于是绝大部分帧被判非法。

### 试过但失败的方案

| 方案 | 做法 | 结果 |
|---|---|---|
| A | 改 `HAL_UARTEx_ReceiveToIdle_IT` 收 64 字节，块内搜索合法帧 | 遥控仍无反应 |
| B | 保留 18 字节定长接收，保留上一帧拼成 36 字节后滑动搜索 | 遥控仍无反应 |

两次改动都**已回退**。注意：排查过程中我曾把「调试器把 CPU halt 住导致的
全零读数」误判成「固件卡死」，因此错误地回退过可能有用的代码——
所以上面两个方案**是否真的无效，仍存疑**，重启后可能表现不同。

### 下一步（不要再用推测）

**先用串口助手或逻辑分析仪抓一次原始字节流**，确认三个数：

1. 一帧到底多少字节（18 / 19 / 25 ？）
2. 帧头是不是 `0x20 0x00`
3. 帧间隔多少毫秒

拿到这三个数，代码一次改对。**在确认之前不要再改解码逻辑。**

### 现在的做法（2026-11-16 夜已备好）

不用串口助手、也不用动接线（信号线并联取信号在这种线束上不好做）：固件里加了一段
**只采集不解析**的抓包代码，用 J-Link 把 RAM 导出来离线分析。

- 固件：`Chassis/Task/component/comm_task.cpp` 的 `kDbusCapture`（USART3 换 ReceiveToIdle 切块）
- 工具：`tools/jlink.ps1 -Action dump-dbus` → `tools/dbus_capture.py --dump dbus_cap.bin`
- 步骤：见 [dbus_capture.md](dbus_capture.md)

分析脚本会把「帧长 × 相位」全枚举一遍，判据是**拨杆只能 1/2/3 + 四个摇杆 11 bit 在
364~1684**，合法率 ≥ 90% 才算对。所以不需要先猜帧长就能出结论。

> ⚠️ 另一个已排除的假设：9 位字长 + 偶校验**不会**让 HAL 按 16 位步进写 uint8 缓冲区。
> `stm32f4xx_hal_uart.c` 在 `PARITY_EVEN` 下走的是 `pdata8bits` + 掩码 `0x00FF`，
> 每次步进 1 字节。所以「缓冲区被零填充/窗口漂移」这条路不用再查。

### 兜底方案

把接收机直接接到**云台板**（云台板有独立的 DBUS 口与本地解码路径）。
代码已支持该分支（`local_rc_online`），云台可以脱离底盘转发独立工作。

## 2. 四个轮子完全不转

### 已排除

- 状态机前提：**rc / peer / imu / motors / estop 五个前提全部强制为真，轮子仍不转**
  （台架模式 `kBenchTest`，已默认关闭）
- 因此问题不在状态机，在**电调指令这一层**

### ⚠️ 但那次实验本身是坏的（2026-11-16 夜修正）

台架分支写完 `command_` 就直接 `return`，**漏了 `chassis_->SetCommand(command_, delta_)`**；
而 `Chassis::Update()` 只认 `SetCommand()` 存进去的 `command_`。于是台架模式下
`wheel_vel` 恒 0 → 速度环目标恒 0 → 四个轮子一动不动。

所以「五个前提全为真仍不转」**不能用来排除电调/接线**，它是固件 bug。
同一类问题还有：`g_bench_open_duty` 只有定义、从来没用过 —— 想做的开环测试其实不存在。

两处都已在 11-16 夜修好（台架开关还改成了运行期可写的 `g_bench_enable`，写魔数才生效）。

### 关于「0x201 是两倍」

四轮全不转的情况下，即使真有两个电调都是 ID 1，ID 2/3/4 的轮子仍然会收到各自槽位的电流
——**不可能四个全不动**。所以这个「双倍」解释不了主现象，先别当成结论。

当时的帧计数（来源不明，可能就是加总读出来的）：

```
0x201   36,039 帧    ← 是其他三个的整 2 倍
0x202   18,009 帧
0x203   17,950 帧
0x204   17,906 帧
```

帧计数是**按总线分开记的**（`g_rx_cnt[0][*]` = CAN1，`g_rx_cnt[1][*]` = CAN2），
读的时候**不要加总**。如果 0x201 在两路各有一份、加起来才是别人的 2 倍，
说明两路 CAN 被接成了一条（或跨接），那是接线问题，不是电调 ID 问题。

### 下一步

1. **分总线读嗅探表**：`g_rx_ids[0][*]` / `g_rx_ids[1][*]` 及对应 `g_rx_cnt`，
   不要加总。判读见 [bringup.md](bringup.md) 3.1。
2. **开环占空比测试**（已实现）：台架模式下写 `g_bench_open_duty`，绕过 PID 四轮直给同一电流。
   - 能转 → 问题在 PID/指令链
   - 不转且 `g_can_tx_fail` 在涨 → 发送层（以前这里完全静默，返回值被丢了）
   - 不转且 `g_can_tx_fail == 0`、反馈正常 → 才轮到电调（小灯 / 24V / ID）
3. 需要时再确认四个 C620 的实际 ID（拨码/上位机），应为 1/2/3/4

## 3. pitch 的 CAN2 物理静默

- pitch 在**云台板 CAN2** 上（`0x011`），曾验证过：温度 27/29、工作正常
- 但之后 CAN2 上再也收不到任何帧（连同 `0x203` 一起消失）
- 云台板 CAN1 上只有底盘发来的 `0x200/0x1FF/0x210`，没有任何电机反馈

说明 CAN2 这条链路的物理状态不稳定（接插件/线束），需要查线。
**不是代码问题**：代码侧 `hcan2` 已启动、滤波器已正确配置。

## 4. 踩过的坑（写给后来的人）

### 4.1 J-Link 会把 CPU 停住，读数全是假象

`connect` 之后内核处于 halt 状态，此时读到的 RAM 是**未初始化/冻结**的：

- `uwTick = 0` 且不增长
- `inputs_` 全零、计数器全零

**判断「程序是否在跑」的唯一可靠方法是看 `uwTick` 是否在增长。**
我曾据此误判固件卡死，错误回退了两次代码。

### 4.2 `DBG_IWDG_STOP` 会让看门狗验证失败

`DBGMCU_APB1_FZ` 的 bit12 若为 1，CPU 被 halt 时看门狗**停止计数**，
此时做「停喂狗→应复位」的验证永远失败。测试前先清这一位。

### 4.3 达妙电机单独断电会造成死锁

`dm_status_.is_enabled` 来自上一次反馈。如果只给电机断电、控制板没复位，
该值残留为 1，`encode()` 就不会再发使能帧，电机静默失能。
已加 `RequestEnable()` + 反馈超时自愈解决。

### 4.4 调参必须带安全裕量

云台曾因 `ki=8` + `int_max=1.0 N·m` 失控飞转：阶跃响应看着完美，
但静置时积分把输出顶到 1 N·m 并保持，yaw 作为自由轴持续加速。

**测试场景覆盖不到的风险，不能留在机器里。**
现在的云台参数：`max_torque=0.25`、`ki=0`、积分限幅 ±0.15、|err|>34° 清零。

### 4.5 判据不等价 = 白做一天

11-16 一天里回退了两次「可能有用的改动」，根因不是代码，是**判据选错**：

- 用「遥控有没有反应」判断 DBUS 解码对不对 —— 但状态机、CAN、电调任何一环断了，
  现象都一样，无法区分
- 用「五个前提全为真」判断电调好不好 —— 但那次台架分支本身漏了一句 `SetCommand()`，
  前提全真时指令依然是 0

选判据的标准：**这个现象只可能由这一个原因引起**。做不到就换判据（比如直接看字节、
直接读电流指令），或者先把手上的测量工具修好。

### 4.6 调试开关别写成编译期常量

`constexpr bool kBenchTest = false` 这种开关，每测一次都要改代码 + 重编译 + 重烧，
两分钟一轮，还容易忘记「板上跑的是哪一版」。现在的做法：

```cpp
volatile uint32_t g_bench_enable = 0;        // 上电默认关
if (g_bench_enable == 0x5A5A5A5A) { ... }    // 魔数才生效
```

好处：J-Link 一条 `w4` 就能开关；复位自动关闭（不会忘了关）；写错值（比如写 1）
不生效。代价：能用调试器改，所以「正式使用必须关」这条得靠复位来保证。

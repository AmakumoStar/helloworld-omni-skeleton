## 1. DBUS 遥控解码失败（最高优先级）

### 现象

```
g_dbus_ev  ≈ +72/秒        ← 接收机确实在发帧，串口也在收
g_dbus_ok  ≈ 0              ← 但几乎没有一帧通过 IsDbusFrameValid
rc_online  = 0              → 底盘卡在 Dead → 输出恒零
```

底盘和云台**都**受影响：云台的摇杆量来自底盘转发（`yaw_des`），
底盘 `rc=0` 时 `yaw_des` 恒为 0，所以云台也无法遥控。

### 已定位的事实

| 项 | 值 |
|---|---|
| 有信号的串口 | **USART3**（USART1/6 事件数恒 0） |
| UART 电气参数 | 100 kbaud / 8 数据位 / 偶校验，与 DBUS 一致 |
| UART 错误计数 | 0（说明不是波特率/校验错） |
| 原始缓冲（某次） | `00 00 04 00 04 20 00 D9 72 ...` |
| 同样数据偏移 2 字节后 | `data[5] = 0xD9` → left=3、right=1（**合法**） |

**结论：数据本身是好的，是接收窗口没有对齐。**

真实 DBUS 帧带 `0x20` 帧头，帧长不是 18；按 18 字节定长接收会让窗口
逐帧漂移，`data[5]`（拨杆字节）落到不同位置，于是绝大部分帧被判非法。

### 试过但失败的方案

| 方案 | 做法 | 结果 |
|---|---|---|
| A | 改 `HAL_UARTEx_ReceiveToIdle_IT` 收 64 字节，块内搜索合法帧 | 遥控仍无反应 |
| B | 保留 18 字节定长接收，保留上一帧拼成 36 字节后滑动搜索 | 遥控仍无反应 |

两次改动都**已回退**。注意：排查过程中我曾把「调试器把 CPU halt 住导致的
全零读数」误判成「固件卡死」，因此错误地回退过可能有用的代码——
所以上面两个方案**是否真的无效，仍存疑**，重启后可能表现不同。

### 下一步（不要再用推测）

**先用串口助手或逻辑分析仪抓一次原始字节流**，确认三个数：

1. 一帧到底多少字节（18 / 19 / 25 ？）
2. 帧头是不是 `0x20 0x00`
3. 帧间隔多少毫秒

拿到这三个数，代码一次改对。**在确认之前不要再改解码逻辑。**

### 兜底方案

把接收机直接接到**云台板**（云台板有独立的 DBUS 口与本地解码路径）。
代码已支持该分支（`local_rc_online`），云台可以脱离底盘转发独立工作。

## 2. 四个轮子完全不转

### 已排除

- 状态机前提：**rc / peer / imu / motors / estop 五个前提全部强制为真，轮子仍不转**
  （台架模式 `kBenchTest`，已默认关闭）
- 因此问题不在状态机，在**电调指令这一层**

### 最可疑的线索：电调 ID 重复

CAN 上四个电调的反馈帧数：

```
0x201   36,039 帧    ← 是其他三个的整 2 倍
0x202   18,009 帧
0x203   17,950 帧
0x204   17,906 帧
```

`0x201` 正好是两倍，最合理的解释是**有两个电调都配置成了 ID 1**。
后果：两个电调抢同一个 `0x200` 电流指令，表现为指令混乱。

### 下一步

1. **确认四个 C620 的实际 ID**（拨码/上位机），应为 1/2/3/4
2. 做**开环电流测试**：绕过 PID 直接给 `0x200` 固定电流
   - 能转 → 问题在 PID/指令链
   - 不能转 → 电调没使能（看 C620 上的小灯）

## 3. pitch 的 CAN2 物理静默

- pitch 在**云台板 CAN2** 上（`0x011`），曾验证过：温度 27/29、工作正常
- 但之后 CAN2 上再也收不到任何帧（连同 `0x203` 一起消失）
- 云台板 CAN1 上只有底盘发来的 `0x200/0x1FF/0x210`，没有任何电机反馈

说明 CAN2 这条链路的物理状态不稳定（接插件/线束），需要查线。
**不是代码问题**：代码侧 `hcan2` 已启动、滤波器已正确配置。

## 4. 踩过的坑（写给后来的人）

### 4.1 J-Link 会把 CPU 停住，读数全是假象

`connect` 之后内核处于 halt 状态，此时读到的 RAM 是**未初始化/冻结**的：

- `uwTick = 0` 且不增长
- `inputs_` 全零、计数器全零

**判断「程序是否在跑」的唯一可靠方法是看 `uwTick` 是否在增长。**
我曾据此误判固件卡死，错误回退了两次代码。

### 4.2 `DBG_IWDG_STOP` 会让看门狗验证失败

`DBGMCU_APB1_FZ` 的 bit12 若为 1，CPU 被 halt 时看门狗**停止计数**，
此时做「停喂狗→应复位」的验证永远失败。测试前先清这一位。

### 4.3 达妙电机单独断电会造成死锁

`dm_status_.is_enabled` 来自上一次反馈。如果只给电机断电、控制板没复位，
该值残留为 1，`encode()` 就不会再发使能帧，电机静默失能。
已加 `RequestEnable()` + 反馈超时自愈解决。

### 4.4 调参必须带安全裕量

云台曾因 `ki=8` + `int_max=1.0 N·m` 失控飞转：阶跃响应看着完美，
但静置时积分把输出顶到 1 N·m 并保持，yaw 作为自由轴持续加速。

**测试场景覆盖不到的风险，不能留在机器里。**
现在的云台参数：`max_torque=0.25`、`ki=0`、积分限幅 ±0.15、|err|>34° 清零。

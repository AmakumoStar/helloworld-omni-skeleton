## 1. DBUS 遥控解码失败（最高优先级）

### 现象

```
g_dbus_ev  ≈ +72/秒        ← 接收机确实在发帧，串口也在收
g_dbus_ok  ≈ 0              ← 但几乎没有一帧通过 IsDbusFrameValid
rc_online  = 0              → 底盘卡在 Dead → 输出恒零
```

底盘和云台**都**受影响：云台的摇杆量来自底盘转发（`yaw_des`），
底盘 `rc=0` 时 `yaw_des` 恒为 0，所以云台也无法遥控。

### 已定位的事实

| 项 | 值 |
|---|---|
| 有信号的串口 | **USART3**（USART1/6 事件数恒 0） |
| UART 电气参数 | 100 kbaud / 8 数据位 / 偶校验，与 DBUS 一致 |
| UART 错误计数 | 0（说明不是波特率/校验错） |
| 原始缓冲（某次） | `00 00 04 00 04 20 00 D9 72 ...` |
| 同样数据偏移 2 字节后 | `data[5] = 0xD9` → left=3、right=1（**合法**） |

**结论：数据本身是好的，是接收窗口没有对齐。**

真实 DBUS 帧带 `0x20` 帧头，帧长不是 18；按 18 字节定长接收会让窗口
逐帧漂移，`data[5]`（拨杆字节）落到不同位置，于是绝大部分帧被判非法。

### 试过但失败的方案

| 方案 | 做法 | 结果 |
|---|---|---|
| A | 改 `HAL_UARTEx_ReceiveToIdle_IT` 收 64 字节，块内搜索合法帧 | 遥控仍无反应 |
| B | 保留 18 字节定长接收，保留上一帧拼成 36 字节后滑动搜索 | 遥控仍无反应 |

两次改动都**已回退**。注意：排查过程中我曾把「调试器把 CPU halt 住导致的
全零读数」误判成「固件卡死」，因此错误地回退过可能有用的代码——
所以上面两个方案**是否真的无效，仍存疑**，重启后可能表现不同。

### 下一步（不要再用推测）

**先用串口助手或逻辑分析仪抓一次原始字节流**，确认三个数：

1. 一帧到底多少字节（18 / 19 / 25 ？）
2. 帧头是不是 `0x20 0x00`
3. 帧间隔多少毫秒

拿到这三个数，代码一次改对。**在确认之前不要再改解码逻辑。**

### 现在的做法（2026-11-16 夜已备好）

不用串口助手、也不用动接线（信号线并联取信号在这种线束上不好做）：固件里加了一段
**只采集不解析**的抓包代码，用 J-Link 把 RAM 导出来离线分析。

- 固件：`Chassis/Task/component/comm_task.cpp` 的 `kDbusCapture`（USART3 换 ReceiveToIdle 切块）
- 工具：`tools/jlink.ps1 -Action dump-dbus` → `tools/dbus_capture.py --dump dbus_cap.bin`
- 步骤：见 [dbus_capture.md](dbus_capture.md)

分析脚本会把「帧长 × 相位」全枚举一遍，判据是**拨杆只能 1/2/3 + 四个摇杆 11 bit 在
364~1684**，合法率 ≥ 90% 才算对。所以不需要先猜帧长就能出结论。

> ⚠️ 另一个已排除的假设：9 位字长 + 偶校验**不会**让 HAL 按 16 位步进写 uint8 缓冲区。
> `stm32f4xx_hal_uart.c` 在 `PARITY_EVEN` 下走的是 `pdata8bits` + 掩码 `0x00FF`，
> 每次步进 1 字节。所以「缓冲区被零填充/窗口漂移」这条路不用再查。

### 兜底方案

把接收机直接接到**云台板**（云台板有独立的 DBUS 口与本地解码路径）。
代码已支持该分支（`local_rc_online`），云台可以脱离底盘转发独立工作。

## 2. 四个轮子完全不转

### 已排除

- 状态机前提：**rc / peer / imu / motors / estop 五个前提全部强制为真，轮子仍不转**
  （台架模式 `kBenchTest`，已默认关闭）
- 因此问题不在状态机，在**电调指令这一层**

### ⚠️ 但那次实验本身是坏的（2026-11-16 夜修正）

台架分支写完 `command_` 就直接 `return`，**漏了 `chassis_->SetCommand(command_, delta_)`**；
而 `Chassis::Update()` 只认 `SetCommand()` 存进去的 `command_`。于是台架模式下
`wheel_vel` 恒 0 → 速度环目标恒 0 → 四个轮子一动不动。

所以「五个前提全为真仍不转」**不能用来排除电调/接线**，它是固件 bug。
同一类问题还有：`g_bench_open_duty` 只有定义、从来没用过 —— 想做的开环测试其实不存在。

两处都已在 11-16 夜修好（台架开关还改成了运行期可写的 `g_bench_enable`，写魔数才生效）。

### 关于「0x201 是两倍」

四轮全不转的情况下，即使真有两个电调都是 ID 1，ID 2/3/4 的轮子仍然会收到各自槽位的电流
——**不可能四个全不动**。所以这个「双倍」解释不了主现象，先别当成结论。

当时的帧计数（来源不明，可能就是加总读出来的）：

```
0x201   36,039 帧    ← 是其他三个的整 2 倍
0x202   18,009 帧
0x203   17,950 帧
0x204   17,906 帧
```

帧计数是**按总线分开记的**（`g_rx_cnt[0][*]` = CAN1，`g_rx_cnt[1][*]` = CAN2），
读的时候**不要加总**。如果 0x201 在两路各有一份、加起来才是别人的 2 倍，
说明两路 CAN 被接成了一条（或跨接），那是接线问题，不是电调 ID 问题。

### 下一步

1. **分总线读嗅探表**：`g_rx_ids[0][*]` / `g_rx_ids[1][*]` 及对应 `g_rx_cnt`，
   不要加总。判读见 [bringup.md](bringup.md) 3.1。
2. **开环占空比测试**（已实现）：台架模式下写 `g_bench_open_duty`，绕过 PID 四轮直给同一电流。
   - 能转 → 问题在 PID/指令链
   - 不转且 `g_can_tx_fail` 在涨 → 发送层（以前这里完全静默，返回值被丢了）
   - 不转且 `g_can_tx_fail == 0`、反馈正常 → 才轮到电调（小灯 / 24V / ID）
3. 需要时再确认四个 C620 的实际 ID（拨码/上位机），应为 1/2/3/4

## 3. pitch 的 CAN2 "物理静默" —— 已定案：**是固件 bug，不是硬件**

> ⚠️ 这条以前写成"CAN2 物理链路不稳定，去查线束"。**那个结论是错的**，
> 白白让人怀疑接线。2026-11-17 晚用 J-Link 读到三个寄存器后一次定案。

### 真实症状

`g_rx_uniq[1] = 0`：云台板 CAN2 **一帧都没收到过**；而 CAN1 上的 `0x12`（yaw 反馈）
约 900 Hz 正常。同时 CAN2 的 `ESR = 0`（TEC/REC/LEC 全 0，无 bus-off）。

### 真因（两个错误叠在一起）

1. **`CanFilter_Init()` 里的结构体没初始化**：`CAN_FilterTypeDef can_filter;` 只填了 7 个
   字段，`SlaveStartFilterBank` 是**栈上的垃圾值**。这个字段 = CAN2 的起始滤波器 bank
   （HAL 写进 `FMR.CAN2SB`）；它一旦是 0，CAN2 就会去用 **bank 0** —— 那是给 CAN1 配的、
   指向 FIFO0 的"全收"滤波器。
2. **云台板的 `can.c` 只开了 `CAN2_RX1_IRQn`**，没开 RX0。于是帧进了 FIFO0，
   而 RX0 中断不触发 → FIFO 满并溢出。

### 决定性证据（复现时照读这三个）

| 寄存器 / 变量 | 读到的值 | 说明 |
|---|---|---|
| `CAN2 RF0R`（`0x4000680C`） | `0x1B` | FMP0=3（满）+ FULL0 + **FOVR0 溢出** → 帧确实在进 |
| `CAN2 IER`（`0x40006814`） | `0x12` | FIFO0/FIFO1 的"收到消息"中断使能了 |
| `CAN2 ESR`（`0x40006818`） | `0` | 无错 → 电机在 ACK，总线是好的 |
| `g_rx_uniq[1]` | `0` | 但 ISR 从来没跑过 → 是中断/NVIC 层的问题 |

判读口诀：**ESR 干净 + RF0R 有积压 = 帧收到了但没人取**，不可能是"线坏了"。

### 修法（两板都改了）

- `CanFilter_Init()`：`can_filter` 改成零初始化，并显式
  `can_filter.SlaveStartFilterBank = 14;`
- 底盘板本来就 RX0/RX1 都开着，所以一直"碰巧没事"；云台板补上 RX0 也行，但修好
  滤波器分配（CAN2 → bank 14 → FIFO1）后，现成的 RX1 中断就能用，不必加 ISR。

### 修好后

`g_rx_uniq[1] = 2`，`g_rx_ids[1][*]` 出现 **`0x011`**（pitch 达妙反馈，约 1 kHz）和
`0x203`（一个轮电调，说明这条 CAN2 与底盘那边有混接）。pitch 随即能正常使能、
`is_enabled = true`、进入 MIT 模式。

## 4. 踩过的坑（写给后来的人）

### 4.1 J-Link 会把 CPU 停住，读数全是假象

`connect` 之后内核处于 halt 状态，此时读到的 RAM 是**未初始化/冻结**的：

- `uwTick = 0` 且不增长
- `inputs_` 全零、计数器全零

**判断「程序是否在跑」的唯一可靠方法是看 `uwTick` 是否在增长。**
我曾据此误判固件卡死，错误回退了两次代码。

### 4.2 `DBG_IWDG_STOP` 会让看门狗验证失败

`DBGMCU_APB1_FZ` 的 bit12 若为 1，CPU 被 halt 时看门狗**停止计数**，
此时做「停喂狗→应复位」的验证永远失败。测试前先清这一位。

### 4.3 达妙电机单独断电会造成死锁

`dm_status_.is_enabled` 来自上一次反馈。如果只给电机断电、控制板没复位，
该值残留为 1，`encode()` 就不会再发使能帧，电机静默失能。
已加 `RequestEnable()` + 反馈超时自愈解决。

### 4.4 调参必须带安全裕量

云台曾因 `ki=8` + `int_max=1.0 N·m` 失控飞转：阶跃响应看着完美，
但静置时积分把输出顶到 1 N·m 并保持，yaw 作为自由轴持续加速。

**测试场景覆盖不到的风险，不能留在机器里。**
现在的云台参数：`max_torque=0.25`、`ki=0`、积分限幅 ±0.15、|err|>34° 清零。

### 4.5 判据不等价 = 白做一天

11-16 一天里回退了两次「可能有用的改动」，根因不是代码，是**判据选错**：

- 用「遥控有没有反应」判断 DBUS 解码对不对 —— 但状态机、CAN、电调任何一环断了，
  现象都一样，无法区分
- 用「五个前提全为真」判断电调好不好 —— 但那次台架分支本身漏了一句 `SetCommand()`，
  前提全真时指令依然是 0

选判据的标准：**这个现象只可能由这一个原因引起**。做不到就换判据（比如直接看字节、
直接读电流指令），或者先把手上的测量工具修好。

### 4.6 调试开关别写成编译期常量

`constexpr bool kBenchTest = false` 这种开关，每测一次都要改代码 + 重编译 + 重烧，
两分钟一轮，还容易忘记「板上跑的是哪一版」。现在的做法：

```cpp
volatile uint32_t g_bench_enable = 0;        // 上电默认关
if (g_bench_enable == 0x5A5A5A5A) { ... }    // 魔数才生效
```

好处：J-Link 一条 `w4` 就能开关；复位自动关闭（不会忘了关）；写错值（比如写 1）
不生效。代价：能用调试器改，所以「正式使用必须关」这条得靠复位来保证。

## 5. 2026-11-17 现场调试：一天修掉 6 个 bug

新车的底盘板（UID `00380028`）第一次上电调试，从"轮子一动不动"走到"四轮直行、
横移、转向方向全对"。下面按发现顺序记录，**每个都给症状 → 真因 → 修法**，
因为其中 4 个都曾被误判成硬件问题。

### 5.1 DBUS 解码：其实是两个 bug 叠在一起

**症状**：`g_dbus_ev ≈ 72/秒` 但 `g_dbus_ok ≈ 0`，`rc_online=0`，底盘永远 Dead。

**真因 A（定长接收滑窗）**：按 18 字节定长接收，一旦上电时正好从帧中间开始数，
窗口就永远错位，`g_dbus_ok` 恒 0，重启才可能重新对上。

**真因 B（判据写错，更隐蔽）**：

```cpp
uint8_t acc = 0;
for (i) acc |= data[i];
if (acc == 0x00 || acc == 0xFF) return false;   // ← 错
```

本意是"整帧全 0 / 全 FF 判非法"，但**按位或等于 0xFF ≠ 每个字节都是 0xFF**。
实测左摇杆推到 0.369 时帧里出现 `0xF5` 和 `0xFA`，`0xF5|0xFA = 0xFF` →
整帧被判非法 → 遥控瞬间掉线 → 状态机 Dead → 推杆没反应。
这就是"遥控有时好有时坏"的元凶，与摇杆位置相关，极难靠现象定位。

**修法**：逐字节判 all-zero / all-FF；接收改成 `ReceiveToIdle`（空闲切块天然对齐）。
主机自测里加了回归用例（那一帧 `00 04 20 00 F5 FA …` 必须通过）。

**抓包定案的数据**（`tools/dbus_capture.py` 分析 128 块）：

| 项 | 值 |
|---|---|
| 帧长 | **18 字节** |
| 帧头 | **没有**（首字节 `00 04` 是摇杆 ch0 的 11 bit） |
| 帧间隔 | **14 ms（71.4 帧/秒）** |
| 解码偏移 | **0**（块内第 0 字节就是 `DT7::decode` 的 `data[0]`） |

### 5.2 一推杆轮子就停（武装互锁写成了"持续检查"）

**症状**：左摇杆一推，四个轮子立刻停；松杆回中 200 ms 后又恢复运动。

**真因**：武装互锁写成了"任一摇杆偏转就把 `arm_ms_` 清零"，于是推杆的同一拍
指令就被清零 —— 底盘永远走不了。本意只是"上电时要求摇杆回中 200 ms"。

**修法**：改成**一次上锁**：只有 `arm_ms_ < kArmHoldMs` 时才检查回中，
上锁后摇杆怎么推都不再清零；退出 Working / 急停时 `OutputZero()` 重新上锁。

### 5.3 CAN 整路静默，只有重启能恢复

**真因**：`can.c` 里 `AutoBusOff = DISABLE`。一次 bus-off（对端没电 / 拔线 / 强干扰）
之后控制器不会自己回到正常态，**连收都停**，只有复位能救。
实测：云台板断电期间自己被 bus-off，之后即使底盘上电，底盘也收不到任何 `0x211`；
给云台板断电重上电立刻恢复。

**修法**：两板四路全部改成 `AutoBusOff = ENABLE`（CubeMX 重新生成会覆盖，注意）。

### 5.4 前推自转、横推堵转（左右轮镜像安装）

**症状**：前推左摇杆 → 车**原地顺时针转**；横推 → 车不动，轮子发出堵转声。

**真因**：麦轮车左右两侧电机/减速器是**镜像安装**的，而 `kWheelDir` 四个都写成
`kDirRev` → 同一条正向电流在左侧是往前推、右侧是往后推 → 左前右后 → 自转；
横移时对角两轮本该反向，方向错的那一对互相顶住 → 堵转。

**修法**：右侧两个（RB、RF）改成 `kDirFwd`。判据是**自转方向**：前推顺时针
（往右转）= 左侧正确、右侧反了。

### 5.5 起步慢、松手还在爬

**真因 A**：静摩擦门槛实测 `raw 655~819`（开环 4% 不动、5% 才转），而
静摩擦前馈 `ff` 只给了 400 —— 输出压在门槛下面，要等积分顶上去才动（约 0.2 s）。

**真因 B**：目标速度为 0 时误差恒为 0，**积分冻结**在上一轮的值上，一直给着
几十~一百多 raw 的电流（实测松手后 `out_` 还是 ±170）→ 轮子慢慢爬。

**修法**：`ff` 400→800，`kp` 150→250，`ki` 150→200；目标为 0 时清积分并输出 0。

### 5.6 "对角线速度不同"—— 不是 bug，是云台坐标系

**症状**：前推左摇杆时，一组对角轮正转、另一组反转，看起来像逆解错了。

**真因**：速度指令定义在**云台坐标系**，`SetCommand(command_, delta_)` 会按
δ 一起解算。当时云台偏了 110°，于是"前"对车体来说是"侧移 + 后退"。
代进麦轮逆解算出的四轮值 (+0.67, −1.45, −1.45, +0.67) 与实测
(+0.79, +0.78, −1.49, −1.33) 几乎一致 —— 逆解完全正确。

**处理**：这是设计行为（"小陀螺模式下平移仍随枪口"是验收加分项）。
测方向时用 `g_ignore_delta = 1` 把 δ 强制清零；正式使用必须为 0。

## 6. 这台车的遥控器与操作映射（实测）

**遥控器没有独立三档拨杆**，只有两个摇杆。实测 DBUS 帧里拨杆字节恒为 `0x0303`
（byte5 高 4 位恒 `0xF`），无论怎么拨都不变 —— 所以拨杆相关的功能全部要改写：

| 原设计 | 这台车实际 |
|---|---|
| 左拨杆下 = 急停 | **左摇杆拉到底（≤ −0.9）并卡住** = 急停 |
| 右拨杆三档 = 三模式 | **右摇杆竖直拨一下切一档**（>0.75 触发，回中 <0.45 解锁，带迟滞） |
| 拨轮 = 小陀螺自旋速度 | 不变（可用） |

模式循环：分离(0) → 跟随(1) → 小陀螺(2) → 分离，**上拨=下一档、下拨=上一档**，
松手保持（原来的"位置映射"方案不行 —— 摇杆是弹簧回中的，按住才能选的话一松手就掉回中位）。

调试用运行期变量（J-Link 直接写，上电默认 0）：

| 变量 | 作用 |
|---|---|
| `g_force_mode` | 1/2/3 → 强制 分离/跟随/小陀螺 |
| `g_estop_force` | 1 → 强制急停（验证"急停→全零"） |
| `g_ignore_delta` | 1 → **所有模式**都按车体系解算（强制忽略 δ）；默认 **0** |
| `g_frame_lead` | 小陀螺坐标系超前补偿系数（s），默认 0.19，见第 7 节 |
| `g_bench_enable` | 写 `0x5A5A5A5A` 才开台架模式（绕过五个联锁） |
| `g_wheel_kp / ki / ff` | 轮速环在线整定 |

> 注意：`g_force_mode`、`g_estop_force`、`g_ignore_delta`、`g_frame_lead` 都是 RAM，
> 复位后回到代码默认值（0 / 0 / 0 / 0.19），所以每次烧录完如果要继续调试，需要重新写一次。

## 7. 2026-11-17 晚：小陀螺（Spin）调试

### 7.1 症状

1. 自旋不匀速：**开始快、随后变慢、最后稳定在较低转速**（操作手原话"3 s 开始变慢"）。
2. 小陀螺自旋时**平移方向往自旋方向偏约 15°**（前后明显，左右"基本准"）；反转自旋偏到另一边，
   路径是**整条斜的直线**（不是起步拐一下）。
3. 小陀螺自旋时**平移明显变慢**。

### 7.2 先量再说：内置 100 Hz 录制

在线单点读内存会被 `connect` halt 住、拿到冻结快照，而"逐渐变慢"是时间过程。
所以在 `robot.cpp` 里加了**只写 RAM** 的录制（`g_trace_*` / `TraceTick()`）：
1 kHz 控制周期里按 100 Hz 存 21 列 × 7 s，进小陀螺且 |w|>0.2 自动触发。
跑的时候 SWD 可以拔掉，跑完插上导出：

```
pwsh -File tools\jlink.ps1 -Action dump-trace -Board chassis -Speed 200
python tools\spin_trace.py --dump spin_trace.bin --plot spin_trace.png
```

判读脚本直接输出 4 条判据（指令是否衰减 / 轮子是否跟住 / 车是否打滑 / 是否有反馈跳变）。

### 7.3 数据否掉的三个假设（别再走回头路）

| 假设 | 数据 | 结论 |
|---|---|---|
| **云台保向力矩拖停底盘** | `delta_` 斜率 = −1.370、IMU yaw = −1.370（三位小数一致）；枪口绝对朝向（IMU yaw+δ）自旋全程只漂 **−3.1°**；轮速环 `out` 峰值 661/3000（22%），从未饱和 | **否**。云台确实在顶 1 N·m，但轮子 22% 就压住了 |
| **两颗电调同 ID 让轮速跳变** | 1 ms 级 jitter 最大 1.87（同 ID 交叠会到几十） | **否**（但 C620 拨码仍未核对，是另一件事） |
| **提闸门能解决纯自旋** | 纯自旋 0.8 rad/s 只需 0.245 m/s，本来就碰不到 0.3 的闸门 | **对纯自旋无效**；闸门只在"自旋+平移"时咬住 |

### 7.4 三个真因与修法

1. **平移坐标系**（"平移随枪口"没生效）：`g_ignore_delta` 当时是 1，全部按车体系。
   → 改 0；`kFrameDelta()` 只让**小陀螺**用真实 δ，分离/跟随仍按车体系（操作习惯 + 底盘不转）。
2. **15° 方向偏**：平移按"下发那一拍的 δ"解算，但整车把速度做出来要 ~0.2 s，这期间底盘又自转
   ω·τ → **实际方向 = R(ω·τ) × 枪口方向**。实测 ω=1.37、偏 15°(0.26 rad) → τ≈0.19 s。
   符号随 ω 翻、整条斜线、静态不偏 —— 三个特征全对上。
   → `δ_eff = δ − g_frame_lead·ω`，ω 取底盘 IMU 的 `yawRate()`（新增，10 ms 低通）。
3. **平移变慢**：自旋 0.245 + 平移 0.15 = 0.395 > 闸门 0.3，被**等比**削到 76%（自旋也一起掉）。
   → `kMaxWheelVelMps` 0.5→0.75，并在 `main_task.cpp` 加 `static_assert`：
   `闸门 ≥ max_vx + max_vy + (半轴距+半轮距)·max_spin_w`，防止以后只改指令上限忘了改闸门。

### 7.5 还没解决：1.71 倍比例

四轮实测 3.18 rad/s（目标 3.13、跟得很紧）时，车实际转 **1.370 rad/s**；
而按 R=0.07786、k=0.30676 只能转 **0.807**。差 **1.70 倍**，且稳态下轮子确实跟住目标，
**不是控制环能解释的**，只能是"轮速 → 车速"这一层的比例标定错。

候选（按可疑程度）：减速比（拓扑图写 14、代码用 19.2，差 37%）、轮半径、几何 k。
**分开量**，别直接改 R 凑数：

1. 卷尺：轮子直径、前后轮心距、左右轮心距
2. 减速箱铭牌：P19（19.2）还是 14:1
3. 直行 2 s 量距离：标称应走 0.30 m；若 0.51 m 说明平移也 1.7×（→ 减速比/轮径），
   若 0.41 m 说明只有 1.37×
4. 需要时手转轮子 5 整圈，读 `angle()` 前后差（一圈应变化 6.283 rad；若 4.583 则实际是 14:1）
